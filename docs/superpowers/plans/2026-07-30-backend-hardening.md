# Backend Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring the Supabase backend under version control, prove the RLS policies actually isolate users from each other, and add the in-app account deletion App Store review requires.

**Architecture:** A new `supabase/` directory holds the CLI-managed backend: migrations captured from the live schema, pgTAP tests run against a local Docker stack, and a Deno Edge Function for account deletion. The client gets one new sync helper (`softDeleteAllCharacters`) and a second destructive-action UI in `AccountSheet.tsx`, styled after the existing `DeleteCharacterModal` type-to-confirm pattern.

**Tech Stack:** Supabase CLI (via `npx`) · Docker · pgTAP · Deno (Edge Functions) · Expo SDK 56 · TypeScript strict · `@supabase/supabase-js` v2 · jest-expo. Verify: `npm run typecheck`, `npm test`, `npm run test:db`.

**Spec:** `docs/superpowers/specs/2026-07-28-backend-hardening-design.md`

**Sequence:** Standalone. Builds on the shipped cloud-sync phases 1–4 (all merged). Not sequenced with the UI rework track — the two touch disjoint files.

- [ ] **Step 3: Read the generated file and confirm it matches expectations**

Open `supabase/migrations/<timestamp>_remote_schema.sql`. It should contain (order may differ):

```sql
create table public.characters (
  id uuid primary key,
  user_id uuid not null references auth.users (id) on delete cascade,
  system text not null,
  data jsonb not null,
  updated_at timestamptz not null default now(),
  deleted_at timestamptz
);

alter table public.characters enable row level security;

create policy "owner can read"   on public.characters for select using (auth.uid() = user_id);
create policy "owner can insert" on public.characters for insert with check (auth.uid() = user_id);
create policy "owner can update" on public.characters for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy "owner can delete" on public.characters for delete using (auth.uid() = user_id);

create or replace function public.set_updated_at()
returns trigger language plpgsql as $$
begin
  new.updated_at = now();
  return new;
end;
$$;

create trigger characters_set_updated_at
  before update on public.characters
  for each row execute function public.set_updated_at();
```

If anything is missing (e.g. the trigger, if it was created outside a tracked migration), stop and add it by hand to the generated file before committing — the baseline must be complete or every later `db reset` will diverge from production.

- [ ] **Step 4: Document the ongoing schema-change workflow**

There's no schema change to make right now — this step just writes down the workflow for the next one, so it isn't reinvented or done unsafely under pressure later. Create `supabase/README.md`:

```markdown
# Supabase backend

Schema lives in `migrations/`, captured from and applied to the project linked via
`supabase link`. Local development runs the full stack in Docker.

## Making a schema change

1. `npm run db:start` (if not already running)
2. Edit schema via the local Studio (`http://127.0.0.1:54323`) or raw SQL against the
   local Postgres instance.
3. `npx supabase db diff -f <descriptive-name>` — generates a migration file from
   what changed.
4. `npx supabase db reset` — replays every migration from empty against the local
   stack, verifying the new one works from a clean state, not just incrementally.
5. `npm run test:db` — pgTAP must still pass.
6. **Before the first push of the day:** `npx supabase db dump -f backup-$(date +%Y%m%d).sql`
   from the production side. The free tier has no point-in-time recovery, so this
   file is the only rollback path if a migration does something unexpected in prod.
7. `npx supabase db push` — applies the migration to production.

## Local stack URLs

- API: `http://127.0.0.1:54321`
- Studio: `http://127.0.0.1:54323`
- A physical device needs the host machine's LAN IP in place of `127.0.0.1`.
- The Android emulator needs `10.0.2.2` in place of `127.0.0.1`.
```

## Task 5: Account-deletion Edge Function

**Files:**
- Create: `supabase/functions/delete-account/index.ts`

- [ ] **Step 1: Write the function**

```typescript
// supabase/functions/delete-account/index.ts
import { createClient } from 'jsr:@supabase/supabase-js@2';

Deno.serve(async (req) => {
  if (req.method !== 'POST') {
    return new Response('Method not allowed', { status: 405 });
  }

  const authHeader = req.headers.get('Authorization');
  if (!authHeader) {
    return new Response(JSON.stringify({ error: 'Missing Authorization header' }), {
      status: 401,
      headers: { 'Content-Type': 'application/json' },
    });
  }

  // A client scoped to the caller's own JWT — used only to resolve who they are.
  // Never used to perform the deletion itself.
  const callerClient = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_ANON_KEY')!,
    { global: { headers: { Authorization: authHeader } } },
  );

  const { data: userData, error: userError } = await callerClient.auth.getUser();
  if (userError || !userData.user) {
    return new Response(JSON.stringify({ error: 'Invalid or expired session' }), {
      status: 401,
      headers: { 'Content-Type': 'application/json' },
    });
  }

  // A service-role client — the only place in the system with this privilege — used
  // solely to delete the id resolved above. It never accepts a client-supplied id.
  const adminClient = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!,
  );

  const { error: deleteError } = await adminClient.auth.admin.deleteUser(userData.user.id);
  if (deleteError) {
    return new Response(JSON.stringify({ error: deleteError.message }), {
      status: 500,
      headers: { 'Content-Type': 'application/json' },
    });
  }

  return new Response(JSON.stringify({ ok: true }), {
    status: 200,
    headers: { 'Content-Type': 'application/json' },
  });
});
```

- [ ] **Step 3: Implement it**

```typescript
/** Soft-delete every one of the signed-in user's characters — the reversible half of
 *  account deletion ("Remove cloud data"). Scoped by user_id in addition to relying on
 *  RLS, so the intent is explicit even though RLS alone would already enforce it. */
export async function softDeleteAllCharacters(session: Session | null): Promise<void> {
  if (!supabaseConfig.enabled || !session) return;
  const { error } = await supabase
    .from('characters')
    .update({ deleted_at: new Date().toISOString() })
    .eq('user_id', session.user.id);
  if (error) console.warn('[sync] soft-delete-all failed:', error.message);
}
```
